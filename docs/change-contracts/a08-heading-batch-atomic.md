## Existing mechanism and trace

`operations_console_app.create_console_app` registers POST `/review/headings/batch-confirm`; `review_workboard_v1.install_review_workboard` replaces it with a redirect wrapper that invokes the original endpoint. Authentication yields actor identity; the endpoint constructs optional interaction evidence and calls `OperationsConsole.batch_confirm_headings`. The command checks structure eligibility and sequentially invokes `review_object`, updating its revision pin after each member. Each member owns `_atomic_snapshot_mutation` and `_commit_prepared_store`. Local commits write objects, envelope, bindings and ledger under the reentrant process/file lock. Runtime MRO adds document and review PostgreSQL mixins and rebuildable file mirrors. `workflow_transaction` binds participant `_connect` methods to one context-local connection. Review events use `buffer_events`. PostgreSQL object writes lock workflow.documents and use revision tokens; ordinary concurrent writes may merge disjoint objects. Existing rollback contexts skip snapshot conflicts and otherwise may write captured bundles back to PostgreSQL.

Local real-HTTP regression on unchanged main: second bindingwrite raises OSError, response 500, earlier approval remains after console restart. This is local causal evidence, not production or native PostgreSQL evidence.

## Stateful Class B overlay

Domain entity/aggregate: mutable WorkingRevision's selected structural review batch; kernel/backend orchestration owns authoritative state, HTTP owns only input and redirect.
Invariant(s): all selected members use existing review rules; a supplied snapshot revision must match exactly before any own write; one batch has one commit/rollback boundary; rollback does not write old state over a concurrent winner; published work remains immutable.
Durable state before: unconfirmed eligible structure with exact object history, bindings, envelope, object revision and ledger.
Durable state after: all selected structures confirmed under the existing exact review tuples, audit evidence and review_pass projection. Other objects, source identity/bytes, content decisions, publications and serving authority unchanged.
Transaction boundary: validation plus every member write and final audit flush/commit. Local storage uses its shared store lock and captured-file rollback; PostgreSQL uses one outer native transaction and snapshot-row lock, including identity/document/review participants. Mirrors are disposable in PostgreSQL mode.
Failure/recovery result: local error restores captured files while holding the writer lock; PostgreSQL rolls back natively and reloads mirrors from authority, without compensating database writes. Restart reads the same durable result. No claim of file-store power-loss atomicity across files.
Duplicate execution / idempotency result: duplicate IDs are normalized once in input order. Exact semantic repeats use existing review_object behavior. Reusing a stale supplied revision conflicts even if the content was previously approved. No new idempotency store.
Concurrency result: local requests serialize under the shared-root file lock; native PostgreSQL also locks the snapshot row before reads/validation. Two requests with the same supplied revision cannot both make a transition. No adoption of another writer's revision; existing multi-instance deployment restriction remains.
Audit/evidence requirement: existing per-object review events and exact bindings share the batch commit; no success evidence for discarded own work.

## Rewrite mitigation

Rewrite target: only heading-batch mutation ownership; per-object review rules and unrelated commands stay intact.
Why local patching is insufficient: simply wrapping the loop retains conflict rollback skipping and PostgreSQL compensating-write hazards.
Current authority/writer/reader map: base OperationsConsole owns file-backed snapshots/maps/ledger; PostgreSQL document store owns envelope/object history, review store owns bindings/events, identity store owns roles. Batch HTTP original/wrapper and direct command are entrants; review_object is the reused writer; `_save_objects_pinned`, `_save_envelopes`, `_save_bindings`, ledger append and PostgreSQL write_bundle/replace_snapshot_bindings/buffer flush are downstream writers. Eligibility, mutable-work guard, role checks, object reads and revision checks consume this state. Startup remirroring consumes PostgreSQL authority. Other review/repair/publication writers use existing lock/revision protocols and are not replaced.
Supported runtime topologies: local OperationsConsole/durable subclasses; PostgreSQL document authority with local review files; PostgreSQL document+review authority, including complete/badge and Azure publication subclasses. Azure storage/publication adapters are unchanged; no external Azure calls are test evidence.
Persisted-state impact: no schema, identity, source, review-policy or historic-data migration. Successful batch keeps existing per-member history and audit format.
Compatibility/migration plan: additive batch boundary with existing participant binding/transactions. No dual authority or backfill; ordinary single-object commands retain current boundary.
Rollback/recovery plan: failed native transaction reloads authority; local rollback restores only while holding its exclusive writer lock. Code rollback restores prior batch behavior and does not undo committed reviews; no destructive data rollback.
Cutover trigger: review and required isolated acceptance evidence before merge; deployment separately authorized. No runtime configuration switch.
Cleanup/decommission criteria: no temporary dual writer; thread-local batch-scoped marker always cleared in finally; another request cannot borrow its bypass. Unrelated rollback mechanisms are outside this repair.
Failure blast radius: selected snapshot batch and shared local maps/ledger under the writer lock. PostgreSQL authority remains one transaction; disposable mirrors may need remirroring after failure.
Adversarial proof matrix: member/write-position/late-conflict/final-commit errors; duplicate IDs; fresh/stale repeats; same-revision concurrent HTTP requests; committed winner preservation; rejected role/named-reviewer/eligibility/published work; direct command; local/PG/mixed MRO; fresh readers and restart. Tests must distinguish native database evidence from local and injected failures.
